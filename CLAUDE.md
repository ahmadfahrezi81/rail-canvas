## What this is

**Rail Canvas** — a pixel canvas in the style of r/place, built as a light copy of the tea-pos architecture in Go, and run on Railway as a stress test of its service types. Players in a space share a 256×256 canvas, place one pixel at a time with a cooldown, and see every placement live.

Learning is the point. The structure matters more than the feature list.

## Layered Architecture

Grouped **by layer**, like tea-pos — `service/pixels.go`, not `pixels/service.go`. Never skip a layer.

```
handler     internal/handler    HTTP: auth context, validate, call service, respond
    ↓
service     internal/service    business logic and transactions
    ↓
store       internal/store      queries, generated by sqlc
```

| Layer | May use | Must NOT use |
| --- | --- | --- |
| **handler** | service, generated API types, `httpx` | `store`, SQL, business logic |
| **service** | `store`, `platform` clients | `net/http` types |
| **store** | — (generated) | anything written by hand |

**Every error response goes through `httpx`.** One body shape: `{"error": "..."}`. Unexpected errors use `httpx.HandleError(w, r, op, err)`, which logs the real error and returns a generic 500 — internals never reach a client. chi's own 404/405 are routed through `httpx` too.

**Generated code is never edited** — `internal/store/` (sqlc) and `internal/apigen/` (oapi-codegen), the way tea-pos treats `packages/db/types.ts`. Change the SQL or `openapi.yaml` and regenerate.

## Middleware chain

Order is set in `routes()` in `cmd/api/main.go`. Today:

1. `RequestID` — fresh id per request, in the context and the `X-Request-Id` response header. A client-sent id is **ignored on purpose**: it could be forged to impersonate another request in the logs.
2. `Logger` — one `slog` line per request. `/health` logs at debug, so healthchecks do not drown the log.
3. `Recover` — panic becomes a logged 500. `http.ErrAbortHandler` is re-panicked.

Joining later, in this position: real client IP (Step 5), timeout and body size limit, CORS for the Pages origin (Step 4), auth and tenant (Step 5), rate limit (Step 5).

## Logging

`slog` JSON to stdout, which is what Railway's log view reads. Use `slog.InfoContext(ctx, ...)` / `ErrorContext` inside a request — `middleware.ContextHandler` adds `request_id` to every line written with a request context, so it is never passed around by hand. Every line carries `service` and `env`.

## Rules carried from the plan

These do not have code yet. They are here so the first code that touches them follows them.

- **Tenancy.** `space_id` is the tenant id. Every query on a space-owned table filters on it in Go, and RLS (`FORCE ROW LEVEL SECURITY`, `current_setting('app.tenant_id', true)`) backs it up. Never take a space id from a request body. The API connects as the `app` role, never as `postgres`.
- **Postgres is the source of truth.** Redis and the bucket only hold what can be rebuilt or re-uploaded.
- **Everything outside Postgres carries the space in its name**: Redis keys `space:{s}:…`, bucket paths `spaces/{s}/…`.
- **Migrations**: `make migrate-new name=…`, never a hand-named file. One focused change, backward-compatible (add first, drop later). Never run on API boot.
- **Every read declares its freshness** in a comment: `live`, a TTL, or `immutable` — as in tea-pos.
- **A deliberate choice gets its reason written next to it.** Undocumented, it decays into an accident.
- **Secrets** live in Railway variables only — never in git, never in the Vite build. Every variable is listed in `.env.example`.

## Deploying

Railway builds the root `Dockerfile`. The api service reads `railway.api.json` (set as the service's config file path): healthcheck `/health`, start command `/app/api`, restart on failure. Railway sends `SIGTERM` before replacing a deploy; the API stops accepting, lets in-flight requests finish within `SHUTDOWN_TIMEOUT_SECONDS`, then exits.

`/health` is deliberately dependency-free: a database blip must not make Railway restart a healthy API.
