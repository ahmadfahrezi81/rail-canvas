## Quick Start

```bash
make dev             # run the API on :8080 (reads .env)
make check           # gofmt, go vet, go test, frontend build — most of what CI runs
make test-db         # tests including the database ones, against rail_canvas_test
make generate        # regenerate apigen (openapi.yaml) and store (sqlc)
make migrate-new name=create_things   # never name a migration by hand
make migrate-up      # apply migrations by hand (needs a public database address; production migrates on deploy)
make web-dev         # frontend on :5173 (needs web/.env.local with VITE_API_URL)
make help            # all targets
```

First space and owner, once per database (password is prompted, never a flag):
`set -a; . ./.env; set +a; cd api && go run ./cmd/cli bootstrap -space-name … -space-slug … -email … -name …`

Tools (goose, sqlc, oapi-codegen) run pinned through `go run pkg@version` in the `Makefile` — nothing is installed globally. The module declares Go 1.27; an older local `go` downloads that toolchain into the module cache by itself.

`make docker-build` needs a running Docker daemon. Local Docker is optional — Railway builds the same `Dockerfile` on every deploy.

Environment variables are listed, with comments, in `.env.example`. `.env` is git-ignored and holds local values only.

## What this is

**Rail Canvas** — a pixel canvas in the style of r/place, built as a light copy of the tea-pos architecture in Go, and run on Railway as a stress test of its service types. Players in a space share a 256×256 canvas, place one pixel at a time with a cooldown, and see every placement live.

Learning is the point. The structure matters more than the feature list.

## Layered Architecture

Grouped **by layer**, like tea-pos — `service/pixels.go`, not `pixels/service.go`. Never skip a layer.

```
handler     internal/handler    HTTP: auth context, validate, call service, respond
    ↓
service     internal/service    business logic and transactions
    ↓
store       internal/store      queries, generated by sqlc
```

| Layer | May use | Must NOT use |
| --- | --- | --- |
| **handler** | service, generated API types, `httpx` | `store`, SQL, business logic |
| **service** | `store`, `platform` clients | `net/http` types, raw SQL |
| **store** | — (generated) | anything written by hand |

**Every error response goes through `httpx`.** One body shape: `{"error": "..."}`. Unexpected errors use `httpx.HandleError(w, r, op, err)`, which logs the real error and returns a generic 500 — internals never reach a client. chi's own 404/405 are routed through `httpx` too.

**The handler never sees store types.** Services return their own types (`service.Canvas`); handlers map them to `apigen` types.

**Every space-scoped call goes through `service.inTenant`.** It opens a transaction and sets `app.tenant_id` (the `SET LOCAL` form) before any query, so RLS always has a tenant. Queries still filter on `space_id` as a second check.

**Frontend layers, same contract as tea-pos:** api client (`lib/api/client.ts`) → hook (`lib/hooks/`) → component. A component never imports the client; a hook never calls `fetch`. TypeScript stays on 5.x: `openapi-typescript` needs its JavaScript API, which TypeScript 7 dropped.

**Generated code is never edited** — `internal/store/` (sqlc) and `internal/apigen/` (oapi-codegen), the way tea-pos treats `packages/db/types.ts`. Change the SQL or `openapi.yaml` and regenerate.

## Middleware chain

Order is set in `routes()` in `cmd/api/main.go`. Today:

1. `RequestID` — fresh id per request, in the context and the `X-Request-Id` response header. A client-sent id is **ignored on purpose**: it could be forged to impersonate another request in the logs.
2. `Logger` — one `slog` line per request. `/health` logs at debug, so healthchecks do not drown the log.
3. `Recover` — panic becomes a logged 500. `http.ErrAbortHandler` is re-panicked.
4. `RealIP` — client IP from `REAL_IP_HEADER` (Railway's `X-Real-IP`) only, never `X-Forwarded-For`, which a client can append to. Falls back to the TCP peer locally.
5. `CORS` — only origins in `CORS_ORIGINS` may call the API from a browser (the Pages site, its previews, localhost).
6. `Auth` — a valid `Authorization: Bearer` token puts the user in the context. No or bad token means no user; each handler that needs one returns 401. Checked live on every request, deliberately: a cached session would keep a suspended user working.

Joining later: timeout and body size limit.

## Auth and spaces

- **The space is in the URL** (`/spaces/{spaceId}/…`). A space route calls `Server.member` first: no user → 401, not a member → **404** (strangers cannot tell a space exists).
- **Tokens and invite codes are random and stored only as SHA-256.** Passwords use bcrypt (cost 12). Unknown email and wrong password give the same error and the same timing.
- **Invites are redeemed in one `UPDATE … WHERE used_at IS NULL AND expires_at > now()`**, so a code cannot be used twice even under a race (tested).
- **Rate limits live in the handler**, where the parsed body is: login per email + IP and per IP, signup and join per IP. All k6 traffic shares one IP, so raise these in staging before a load test.

## Realtime

- **Placing goes through REST; the socket only announces.** `service.Pixels.Place` claims the cooldown, writes `pixels` and `canvas_pixels` in one transaction, and publishes `pixel:placed` **after** the commit. Never publish inside a transaction.
- **Two API copies (Railway replicas) share placements through Redis pub/sub** (`realtime.Bus`). `Publish(space, canvas, msg)` delivers to this copy's sockets, then `PUBLISH`es on `space:{s}:canvas:{c}` tagged with the copy's id (`RAILWAY_REPLICA_ID`, on every log line as `replica`). One `PSUBSCRIBE space:*:canvas:*` per copy, on its own connection with default timeouts, passes the others' messages on and skips its own: nobody sees a pixel twice.
- **A gap becomes a reload, never a wrong board.** A listener that reconnects sends its sockets `resync`; a copy that could not announce a pixel sends `resync` for that canvas once Redis answers (checked every 30 s). The frontend reloads the board on `resync`. Stats line: `bus_published`, `bus_received`, `bus_resyncs`.
- **Never keep shared state in the process.** With two copies, anything in memory exists twice: timers fire twice, counts split, sockets are only half known. It goes in Postgres or Redis.
- **The cooldown claim is one atomic `UPDATE space_members … WHERE last_placed_at <= now() - cooldown RETURNING`.** No row means too soon. Five simultaneous clicks place one pixel (tested).
- **`/ws` is mounted directly on the router**, outside the generated interface: an upgrade hands the connection over. Login is a single-use 30-second ticket from `POST /ws/ticket`, because browsers cannot send `Authorization` on a WebSocket.
- **Message shapes live in `openapi.yaml`** (`WSClientMessage`, `WSServerMessage`), unreferenced by any path; `oapi-codegen.yaml` sets `skip-prune` so Go keeps them.
- **The hub never waits on one client.** A full send buffer (64) disconnects that client; it reconnects and reloads. `http.Server.Shutdown` does not close upgraded connections, so `hub.Close` is registered with `RegisterOnShutdown`.
- **`canvas_pixels.pixel_id` has no foreign key**, on purpose: history retention must be able to delete pixels still on the board. It is a version number.
- **Frontend:** `useLiveCanvas` connects, subscribes, *then* loads the board and replays what arrived meanwhile; each cell keeps the newest `pixelId` and ignores older ones. Placing is optimistic: draw on click, undo if the server refuses (unless a newer pixel landed there).
- **A coder/websocket read with a timed-out context closes the connection.** Matters in tests.

## Templates and the bucket

- **The bucket is private; the API signs URLs.** An upload is three calls: `POST …/templates` checks the limits and signs a 5-minute upload URL with the size and type in the signature (the bucket refuses any other file); the browser `PUT`s straight to the bucket; `POST …/complete` checks the stored file and marks it `ready`, or deletes it and marks it `rejected`. Downloads are signed for an hour and shown as a plain `<img>`.
- **Uploads are untrusted.** PNG only, 1 MB, 256 × 256. The size comes from `png.DecodeConfig` on the first bytes: the server never decodes a whole image (a decompression bomb claims huge dimensions in a tiny file).
- **Object keys are built by `service.TemplateKey`** from the URL's space and a server-made id: `spaces/{space}/templates/{id}/original`. Never from client input.
- **`service.ObjectStore` is the bucket's interface**; `platform.Bucket` is the real one, tests use a fake. Without `S3_*` the API runs and the template endpoints answer 503.
- **Bucket CORS** is set from `CORS_ORIGINS` by `cli bucket-cors`. Railway's buckets do not match wildcard origins, so Pages preview sites cannot upload.

## Snapshots

- **Hourly snapshots** (`Snapshots.Pass`, run by the worker; see Cron services): every canvas that changed since its last snapshot becomes a PNG, one pixel per cell, at `spaces/{s}/snapshots/{c}/{hour}.png` in the templates bucket, with a `snapshots` row. One transaction per canvas reads the cells with their `pixel_id`, claims the row (`UNIQUE (canvas_id, taken_at)`: a pass run twice makes one), uploads, commits; a failed upload leaves no row.
## The bot (Telegram, a Railway Function)

- **`functions/webhook/index.ts` is the Railway Function `bot`**: Bun, one file, no packages (`fn()` in `.railway/railway.ts` embeds it in the start command, at most about 98 KB). It checks Telegram's `X-Telegram-Bot-Api-Secret-Token` in constant time before reading anything (401), understands `/link`, `/place`, `/help`, calls the API at `http://rail-canvas.railway.internal:8080` with `X-Webhook-Secret`, and **always answers Telegram 200**, with the reply as a `sendMessage` in its own response (no bot token anywhere). Private chats only
- **The API never trusts the chat account alone.** A member makes a one-time code on a canvas page (`POST …/bot-link-code`, 8 characters, 10 minutes, SHA-256 only); `/link CODE` redeems it in one `UPDATE … WHERE used_at IS NULL` and writes `bot_links` (one Telegram account → one user and canvas; linking again replaces). `/webhooks/bot/pixels` looks the account up and places with `Pixels.PlaceAs`: active user, still a member, the same cooldown as the web, `source = 'bot'`, live to every copy
- **`/webhooks/bot/*` is for our Function, not browsers.** `X-Webhook-Secret` is compared with `WEBHOOK_SECRET` by SHA-256 in constant time; `/link` is rate limited per Telegram account
- **Colour names live in the palette** (`Palette.Names`, `Palette.Color`): the bot sends a word or an index, the API resolves it
- **Test the Function in Railway's own image**, as CI does: `docker run --rm -v "$PWD/functions/webhook:/src:ro" -w /src --entrypoint bun ghcr.io/railwayapp/function-bun:1.4.0 test`. The server starts only under `import.meta.main`, so tests import `handle` with a fake API

## Redis

Railway Redis 8.2, private network only (`REDIS_URL`, a reference). It holds copies and short-lived state; **Postgres stays the source of truth, and with Redis down nothing returns an error.** `service.Redis` wraps the client: a nil `*Redis` means no Redis, and every use has a fallback.

- **Board cache** (`boardcache.go`): `space:{s}:canvas:{c}:board`, one byte per cell, plus `…:ver` (cell → `pixel_id:color`). Each placement, after its commit, runs the compare-and-set Lua script: an older pixel never overwrites a newer one. A miss rebuilds from Postgres once (`singleflight` in the process, a 5-second `SET NX` lock across copies), and the rebuild script merges with `ver` so a pixel announced mid-rebuild survives. The board expires every 10 minutes, so any drift heals.
- **Cooldown** (`cooldown.go`): a Lua check of when the member last placed, against *this* canvas's cooldown (the turn is per space, the cooldown per canvas). It only refuses early; Postgres's claim stays the rule. A failed placement releases it; a Postgres refusal sets it to Postgres's time.
- **Rate limits** live in Redis via `redis_rate` (`rate:{name}:{key}`), so every API copy shares the count; memory when Redis fails.
- **WebSocket tickets**: `ticket:{sha256}` with a 30-second expiry, redeemed with `GETDEL`, then the user is checked active. `ws_tickets` is the fallback.
- **The breaker:** after any Redis failure, Redis is skipped for 5 seconds (`Redis.Up`), so an outage costs one timeout, not one per call. Client timeouts are short (dial 500 ms, read/write 200 ms) and never retried. A board that missed a placement while Redis was skipped is dropped before its next read.
- **Stats line** adds `redis_ok`, `redis_errors`, `board_hits`, `board_misses`.

## The worker

`/app/worker`, the same image as the API, the Railway service `worker`. It takes jobs from Redis with `asynq` (`internal/jobs`) and does the slow work, so the API only does fast things.

- **Jobs:** `template:thumbnail` (queued by `Templates.Complete`: a copy at most 64 × 64, nearest neighbour, `thumb_key`), `snapshots:pass` (queued by the `snapshot` cron service with the hour as its task id, so it is queued once however often it runs), `timelapse:build` (queued by `POST …/timelapses`: an animated GIF of the newest 240 snapshots).
- **Services see only `service.Queue`**, an interface; `jobs.Client` is the real one, tests use a fake. Never assign a nil `*jobs.Client` to it: an interface holding a nil pointer is not nil.
- **Retries: at most 3, exponential** (10 s, 20 s, 40 s, plus up to 20% jitter), the owner's call. `jobs.LastAttempt` tells a handler that a failure now archives the job; the timelapse job then marks its row `failed` so nothing stays `pending`.
- **Every job is safe to run twice** (a retry may repeat work that half-succeeded).
- **Without the queue:** thumbnails are skipped (the full image shows), `cli snapshot` takes the hourly pass itself, a timelapse request answers 503 and leaves no row. Queueing shares the API's Redis circuit breaker.
- **Concurrency 2, Postgres pool 4.** On `SIGTERM` running jobs get 20 seconds; a job cut off goes back in the queue. The worker refuses to start without `REDIS_URL` or the bucket.
- **Stats:** the API's line adds `queue_pending`, `queue_active`, `queue_retry`, `queue_archived`; the worker writes its own (`jobs_done`, `jobs_failed`, its pool).

## Cron services

Railway starts these on a schedule (UTC); each run does its work and exits, so nothing runs or
bills between runs. Same image as the API, `restartPolicyType: "NEVER"`. **No timer runs inside
the API**: with two replicas it would fire twice.

- **`snapshot`**, `0 * * * *`: `/app/cli snapshot` queues this hour's `snapshots:pass` for the worker; without Redis it takes the pass itself
- **`cleanup`**, `0 20 * * *` (an hour after the backup): `/app/cli cleanup` (`service.Cleanup`) deletes expired sessions, tickets and invites, pixel history older than 30 days (never the board), timelapses beyond the newest 10 per canvas, and uploads that never completed. `-dry-run` only counts. A file is deleted before its row, so a failed file delete keeps the row for the next run; pixels go 5,000 per transaction, per canvas. healthchecks.io ping as for the backup (`HC_PING_URL`)
- **A run must end on its own** (5 and 15 minute limits): Railway skips the next run while one is still going
- **Release away from :50–:05 UTC.** Every merge into `main` redeploys every production service; a cron service mid-deploy at its scheduled time skips that run. Pushes to `staging` touch only staging
- **A new rule for a new table goes in `cleanup.go`** with a test on both sides of its line

## Logging

`slog` JSON to stdout, which is what Railway's log view reads. Use `slog.InfoContext(ctx, ...)` / `ErrorContext` inside a request — `middleware.ContextHandler` adds `request_id` to every line written with a request context, so it is never passed around by hand. Every line carries `service` and `env`.

**The stats line** (`msg=stats`, every 30 seconds): `ws_clients`, `ws_subscriptions`, `ws_dropped_slow`, `db_in_use`, `db_idle`, `db_max`, `db_waited_total`. Later steps and the load test are read against it; add fields, do not rename them.

## Rules carried from the plan

- **Tenancy.** `space_id` is the tenant id. Every query on a space-owned table filters on it in Go, and RLS backs it up: `ENABLE` + `FORCE ROW LEVEL SECURITY`, one policy per table comparing `space_id` with `current_tenant_id()` (NULL when unset, so nothing matches). A child table that copies `space_id` uses a composite foreign key `(parent_id, space_id)` so the copy cannot drift. Never take a space id from a request body.
- **Roles.** Migrations run as `postgres`. The API connects as `app` (no superuser, no BYPASSRLS), whose password is set by `make db-app-password`, never in git. Tests use `SET ROLE app` and fail if they find themselves a superuser.
- **Postgres is the source of truth.** Redis and the bucket only hold what can be rebuilt or re-uploaded.
- **Everything outside Postgres carries the space in its name**: Redis keys `space:{s}:…`, bucket paths `spaces/{s}/…`.
- **Migrations**: `make migrate-new name=…`, never a hand-named file. One focused change, backward-compatible (add first, drop later). Applied by the pre-deploy command, never on API boot. Seed data goes in `db/seed/` scripts, never in a migration.
- **Every read declares its freshness** in a comment: `live`, a TTL, or `immutable` — as in tea-pos.
- **A deliberate choice gets its reason written next to it.** Undocumented, it decays into an accident.
- **Secrets** live in Railway variables only — never in git, never in the Vite build. Every variable is listed in `.env.example`.

## CI and deploying

**Two environments, two branches** (Step 16). The `staging` branch deploys to Railway's `staging` environment (its own Postgres, Redis and bucket, seeded fake data); `main` deploys to `production`.

```
local branch ─▶ merge into staging ─▶ push (ask the owner first) ─▶ CI ─▶ staging deploys ─▶ staging tests
                                                                                               │
                        production deploys ◀─ CI on main ◀─ owner merges ◀─ PR staging → main ◀┘
```

- **Work happens on a local branch** and is tested locally (`make check`, `make test-db`). Merging into `staging` locally is fine; **pushing `staging` needs the owner's OK** each time (every push is a staging build and deploy)
- **A release is a pull request `staging` → `main`, merged with a merge commit** (never squash: `main` would get a commit `staging` never had, and the next release would conflict). `main` requires the four CI checks and the `staging` status
- **Every real test runs once:** CI on the push to `staging` (the authority), then the staging tests on the deployed staging. The release pull request reuses both (same commit); CI runs again on `main` only because Railway's Wait for CI needs a green run on the merge commit. Production is never tested by writing to it
- **The staging tests** (`staging-tests.yml`, `api/stagingtest/`): after CI on a `staging` commit, wait until staging's `/health` reports that commit, then log in as the seeded owner and check a pixel reaches a WebSocket and the board, the cooldown, a bot link code, a template through the bucket. A few checks of the wiring, not the logic; a commit status `staging` reports the result. It starts on `workflow_run`, never on `push`: Wait for CI waits for every Actions run on a commit, so a run waiting for the deploy would deadlock it

`.github/workflows/ci.yml` runs on every push to `staging` and `main` (not on pull requests):

- `api` — gofmt, vet, `cli migrate` on a throwaway `postgres:18`, then `go test -race` with the database and Redis tests (a `redis:8.2` service)
- `contract` — `make generate`, then fail on any change: generated code is out of date
- `web` — `pnpm build`
- `docker` — builds the `Dockerfile` and `ops/backup/Dockerfile`, shellchecks the backup scripts, pushes nothing

Railway's **Wait for CI** (`checkSuites` in `.railway/railway.ts`) holds a deploy until every Actions run started by the push is green.

**Migrations run on deploy, never on API boot.** `.railway/railway.ts` sets the pre-deploy command `/app/cli predeploy` (`migrate`; give `app` its password if it cannot log in yet, which only a fresh database needs; `seed` when `SEED_OWNER_PASSWORD` is set, never in production; then `bucket-cors`): after the build, before the new version starts, inside Railway's private network, as `postgres` (`MIGRATE_DATABASE_URL`). If it fails, the deploy stops and the old version keeps serving. It holds a Postgres advisory lock, and an older binary (a rollback) applies nothing. The pre-deploy command runs while the old version still serves, which is why every migration must be backward-compatible. The database has no public address.

Railway builds the root `Dockerfile`: start command `/app/api`, healthcheck `/health`. Railway sends `SIGTERM` before replacing a deploy; the API stops accepting, lets in-flight requests finish within `SHUTDOWN_TIMEOUT_SECONDS`, then exits.

`/health` is deliberately dependency-free: a database blip must not make Railway restart a healthy API.

## Railway as code

`.railway/railway.ts` describes production and staging (`ctx.isEnvironment("production")` picks the differences: staging runs one API copy, deploys the `staging` branch, has no `backup` and no `bot`, writes its database URLs as references and holds no production secret). Production: the `api` service (source, start, pre-deploy, healthcheck, Wait for CI, variables) and `Postgres` with its volume. Railway's own format ("Infrastructure as Code"); `railway.json` files are deprecated and are not read.

- **Production changes by release pull request.** `railway-plan.yml` comments production's plan on the PR into `main`; merging is the approval; `railway-apply.yml` applies exactly that plan. A direct push to `main` has no plan and fails.
- **Staging applies on every push to `staging`** (plan and apply in one job, `RAILWAY_TOKEN_STAGING`): a push has no pull request to pin a plan to. A Railway change is therefore tried on staging before it reaches production.
- **Never edit a declared setting in the dashboard.** The next apply fails (the environment changed since the plan); put the change in the file instead.
- **Nothing is deleted by CI.** Removing a resource from the file deletes it on apply, so the apply runs with `confirm-destructive: false`: a plan that deletes anything fails. Postgres stays declared. Deletes are done by hand, with the owner.
- **A plan is only valid for the project as it was.** Any dashboard change after the plan (even pasting a `preserve()` variable's value) makes the apply fail with "The environment changed since this plan was computed". Paste values first, then plan; if it happens, open a new pull request for a fresh plan.
- **A Function's code is part of the plan**, so `functions/**` triggers the plan and apply workflows like `.railway/**`. It deploys on apply, with no Wait for CI (no repository); CI has tested it on the pull request.
- **Railway drops `checkSuites` when it creates a service.** A new service needs a second pull request to apply Wait for CI.
- **Variables are managed by the file, values are not in it.** `preserve()` keeps the value Railway holds. Never `railway config pull --include-variables`.
- **Locally:** `railway config plan --environment production|staging` (read-only) to preview; `apply` only through the workflows.
- The workflows use `RAILWAY_TOKEN` and `RAILWAY_TOKEN_STAGING`, project tokens for `production` and `staging` in GitHub's secrets. A project token reaches one environment only.
- **A new environment gets its databases from the dashboard, never from the file.** Creating staging, the apply made Postgres with the literal text `secret(32, "…")` as its password and Redis with no variables (a bug in Railway's beta engine); every service failed. Create the environment Empty, add its databases with **+ New → Database** and name them `Postgres-<env>` and `Redis-<env>` (service and bucket names are project-wide: `Postgres` is production's; staging's bucket is `templates-staging`, made with `railway bucket create`), then let the file adopt them by name and create the rest. Sync did not work: it brought the databases without their disks, and an empty environment has no Sync button
- **`ctx.randomString()` is not a secret** (a hash of the environment's name and a label): never use it for a password.

## Backups

`ops/backup/` is its own image, `FROM postgres:18` (a `pg_dump` older than the server refuses to dump it). The cron service `backup` runs `backup.sh` at 19:00 UTC: `pg_dump` as `postgres` (as `app`, RLS would empty the dump), `pg_restore --list`, row counts, upload to Cloudflare R2 with `curl --aws-sigv4`, and a healthchecks.io ping for start, success or failure. `restore.sh` brings a backup back into an empty database, creating the `app` role first. Restore, rollback and secret rotation: `docs/runbook.md`.

- **A failure must reach healthchecks.io exactly once.** The scripts use `set -E` (functions inherit the ERR trap), and `on_error` reports only from the main shell (a failure inside `$(…)` would otherwise report twice)
- **Never echo a variable in these scripts**: `DATABASE_URL` holds the `postgres` password and the ping URL is itself a secret. R2 keys reach curl on stdin, never as arguments

## Commits

`type(scope): a sentence saying what changed` — e.g. `feat(api): the service answers /health and shuts down cleanly`. Scopes: `api`, `web`, `ops`, `ci`, `docs`. **No `Co-Authored-By` trailer.**

## Comments

As short as possible: one line, only where the *why* is not obvious from the code. Long reasoning goes in the task file or Notion, not in code.
