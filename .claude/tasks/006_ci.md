# Task 006 — CI, and migrations that run on deploy

**Status: live 2026-10-14 (pull request #1), completed by task 007: Railway never read `railway.api.json` (deprecated Config as Code), so the pre-deploy step and Wait for CI went into `.railway/railway.ts`. Ruleset on `main` and the practice rollback were done there.**

## What changed from the plan

- **CI applies migrations with `cli migrate` itself**, not the goose CLI, so the job tests the exact command Railway runs.
- **Checked in goose's source:** an older binary finds every version it knows already applied, and versions it does not know are ignored, so a rollback's pre-deploy is a no-op. The test confirms it.
- **Railway runs the pre-deploy command without a shell** (exec form, as with the start command). Fine here: the image is distroless and `cli migrate` reads its URL from the environment itself.
- **Local check** ran against a throwaway Postgres 17 in the scratchpad with a stand-in `uuidv7()` (18 has it built in). All tests green, database ones included. CI uses the real `postgres:18`.

Plan: [Rail Canvas, Step 7](https://app.notion.com/p/3ee95a71540581c8af9ac997375758e9) and its
"CI/CD and environments" section.

## The goal

Every change is checked by GitHub Actions before it reaches `main`, and Railway
only deploys a commit whose checks are green. Database migrations reach
production by themselves, from inside Railway, so the database never needs a
public address again. One rollback is practised so it is not new on a bad day.

## Decisions for this step

1. **CI is GitHub Actions**, one file: `.github/workflows/ci.yml`. It runs on
   every pull request **and** on every push to `main`. The push run is what
   Railway's "Wait for CI" waits for; it only looks at checks on the commit it
   is about to deploy.
2. **Four jobs, in parallel**, so a failure names its cause:
   - `api`: gofmt, `go vet`, then `go test` with a throwaway `postgres:18`
     service container. The job runs every migration on it first (that is the
     migration check), then the tests with `TEST_DATABASE_URL` set, so the
     database tests run instead of skipping. The tests already log in as
     `postgres` and `SET ROLE app`, so the `app` role needs no password here
   - `contract`: `make generate`, then `git diff --exit-code`. Fails if
     `apigen`, `store` or `schema.d.ts` is out of date with `openapi.yaml` or the
     SQL
   - `web`: `pnpm install --frozen-lockfile`, `pnpm build` (type-check and build)
   - `docker`: build the root `Dockerfile`, push nothing. Catches a broken image
     before Railway does
3. **Versions are pinned to what runs locally**: Go from `api/go.mod`
   (1.27.1), Node 22, pnpm 10. Tool versions are already pinned in the
   `Makefile`, so CI's generated code matches the laptop's.
4. **Migrations run as Railway's pre-deploy command**, not from CI and never on
   API boot (owner's call, 2026-10-11, option 1 of 2). Railway runs one command
   after the build and before the new version starts, inside the private
   network. If it fails, the deploy stops and the old version keeps serving.
   The other option (CI runs goose over a public database address) would put
   the database back on the internet with the superuser password in GitHub.
5. **`cli migrate`**: a new command in the existing CLI. The migration files
   are built into the binary (`go:embed`), and goose runs as a library
   (`github.com/pressly/goose/v3`, the same version the Makefile pins). It
   takes Postgres's session lock first, so two runs can never apply the same
   migration twice. `railway.api.json` gets
   `"preDeployCommand": ["/app/cli", "migrate"]`.
6. **It connects with `MIGRATE_DATABASE_URL`**, a new variable on the `api`
   service, set to Postgres's private `DATABASE_URL` (the `postgres` user).
   Trade-off, written down: the API service now holds a superuser URL in its
   variables. The API process never reads it (`config` does not load it), and
   moving migrations to their own service would cost an always-present service
   for one command. Revisit if the project grows.
7. **Migrations must still be backward-compatible.** The pre-deploy command
   runs while the old version is still serving, so for a moment old code runs
   on the new schema. This was already a rule; now it is load-bearing.
8. **A rollback must survive the pre-deploy command.** Redeploying an older
   image runs its `cli migrate`, which knows fewer migrations than the database
   has applied. That must succeed and change nothing. A test checks it (below),
   and the practice rollback confirms it on Railway.
9. **`railway.api.json` watches itself.** Its `watchPatterns` gain
   `railway.api.json`, so a config change deploys.
10. **Branch protection on `main`**: changes arrive by pull request, and the
    four jobs must pass. No review needed (one person). From now on work happens
    on a branch, then a pull request, then merge.
11. **Cloudflare Pages is unchanged.** It builds `web/` from GitHub on its own
    and has no "wait for checks"; the `web` job catches a broken build on the
    pull request before it reaches `main`.

## Tests

- **Migrations on an empty database** (the `api` job): every migration applies
  in order on a fresh `postgres:18`
- **The database tests run in CI**, not just on the laptop
- **Rollback test** (`migrate_test.go`, needs `TEST_DATABASE_URL`): on the
  fully migrated test database, run the migrator with only the older half of
  the files; it succeeds and applies nothing
- **`cli migrate` twice in a row**: the second run applies nothing

## Owner's clicks (I write them down; nothing is assumed done)

On Railway, `api` service:

1. **Variables** → add `MIGRATE_DATABASE_URL` = `${{Postgres.DATABASE_URL}}`
   (the private one, not `DATABASE_PUBLIC_URL`)
2. **Settings** → **Wait for CI**: turn on. It appears once the workflow exists
   on `main`. GitHub may ask to accept Railway's updated permissions
3. **Settings** → **Pre-deploy timeout**: 120 seconds, so a stuck migration
   fails the deploy instead of hanging it

On GitHub, `rail-canvas` → Settings → Branches (or Rules):

4. A rule for `main`: require a pull request (0 approvals), require status
   checks `api`, `contract`, `web`, `docker` to pass, block force pushes

## Order of work

1. On a branch: workflow, `cli migrate`, tests, config, docs. **No database
   touched**
2. Open a pull request; watch all four jobs go green (and once red, on purpose,
   with a gofmt slip, to see a failure block it)
3. **Owner** does click 1 (the variable) **before** merging, or the first
   pre-deploy fails for lack of it
4. Merge. Railway builds, runs `cli migrate` (nothing pending, logs "up to
   date"), deploys. Check `/health` and the site
5. **Owner** does clicks 2 to 4
6. **Practice rollback.** In Railway, redeploy the previous deployment; check
   the pre-deploy log, `/health`, and placing a pixel. Then redeploy the latest
   again
7. Tick Step 7 in Notion, update STATUS

## Out of scope

Running migrations on the laptop (the database stays private; `make migrate-up`
only works if a public address is ever added again), a local Postgres for
`make test-db` (CI runs those tests now), staging and PR environments (Step 16),
gating Cloudflare Pages on CI, down migrations in CI (a rollback here is a
redeploy of older code, not a schema rollback).
